# B-TONE-003 読み手視点で書く

skill / CLI 共通プロンプト。

## 該当ガイドライン

§1 チームみらいらしさの反映 / 読み手視点で書く

> 運営側ではなく、マニュアルを読む人の視点で書きましょう。

`severity`: `WARN`

## 判定手順

本文段落から、**運営側目線で書かれている**箇所を抽出する。

検出パターン:

| 問題類型 | 該当例 |
|---|---|
| 主語が運営に偏る | 「運営から〜を配布します」「事務局では〜を行います」（主語をサポーター側にすべき箇所） |
| 専門用語の説明欠落 | 初心者読者（高校卒業直後・政治活動未経験）が知らない用語が説明なしで登場 |
| 運営手続きの内部視点 | 「審査の上で承認します」「内部で確認します」のような、サポーターから見えない内部処理 |
| 命令調・上から目線 | 「〜すること」「〜しなさい」（命令形）の多用。「〜しましょう」「〜してください」が望ましい |

## 除外基準

以下は対象外:
- **法令説明での「（候補者は）〜することができる」**: 候補者主体が文脈上明確
- **明らかに運営からのメッセージとして提示されている節**: 「指揮者の方へ」「リーダー向け」のような前置きがある場合
- **B-TEXT-005 読みにくさで個別検出される専門用語**
- **B-TONE-001 価値観違反で個別検出される内容**

## 判定方針

「初心者サポーターがこの段落を読んで、自分の行動として理解できるか」を判定基準にする。
できない場合のみ検出。

## 出力フィールド

| フィールド | 内容 |
|---|---|
| `paragraphIndex` | 段落のインデックス |
| `snippet` | 該当箇所（30〜80 字、原文ママ） |
| `perspective_issue` | 問題類型: `運営主語` / `用語説明不足` / `内部視点` / `命令調` |
| `suggestion` | 読み手視点に書き換えた案 |
| `reason` | なぜ運営側目線かの判定根拠 |

## 件数上限: 最大 10 件
